# Module 2 Debugging Session - 2026-07-04

## Topic

Ownership, RAII, raw heap allocation, resource leaks, double-free, and dangling owning pointers.

## Prompts And Responses

### Prompt 1

```cpp
int* make_scores(std::size_t count) {
    int* scores = new int[count]{};

    for (std::size_t i = 0; i < count; ++i) {
        scores[i] = static_cast<int>(i * 10);
    }

    if (count < 5) {
        return nullptr;
    }

    return scores;
}
```

Response: the heap allocation is never destroyed when `count < 5`; it leaks.

Follow-up response: two possible fixes are checking `count < 5` before allocation, or deleting the allocation before returning `nullptr`.

Takeaway: prefer not acquiring a resource until it is needed. If a raw resource is acquired, every exit path must release it or transfer ownership clearly.

### Prompt 2

```cpp
int* scores = make_scores(6);
std::cout << scores[0] << "\n";
delete[] scores;
delete[] scores;
```

Response: expected sanitizer complaint is that `scores` is deleted twice.

Correction/refinement: ASan can track that the allocation was already freed, but the raw pointer variable itself does not know. After `delete[] scores`, `scores` still contains the old address and is dangling unless reassigned.

Follow-up response: assigning `scores = nullptr;` makes a later `delete[] scores;` harmless because deleting `nullptr` is a no-op.

Takeaway: nulling a raw pointer can protect that one pointer variable from a repeat delete, but it does not solve ownership design if other raw pointers still hold the same owning address.

## Mistakes

- Initially relied on manual cleanup reasoning instead of designing ownership around RAII.
- Needed clearer distinction between sanitizer/runtime tracking and the raw pointer value itself.
- Needed to remember that `delete` does not change the pointer variable.

## Conventions Learned

- Prefer not acquiring a resource until it is needed.
- If a raw resource is acquired, every exit path must release it or transfer ownership clearly.
- Setting one raw pointer to `nullptr` after `delete` can prevent repeated delete through that variable, but does not fix shared ownership confusion.
- Prefer RAII objects over raw owning pointers.
