# Module 1 Debugging Session — 2026-07-04

## Topic

Types, references, const correctness, pointer observation, ownership transfer, and lifetime.

## Prompts And Responses

### Prompt 1

```cpp
void print_name(std::string& name) {
    std::cout << name << "\n";
}

int main() {
    const std::string user = "Ada";
    print_name(user);
}
```

Response: parameter is `std::string&`; argument is `const std::string&`.

Correction: the argument object is `const std::string`; the issue is that a non-const lvalue reference cannot bind to a const object.

Takeaway: read-only parameters should use `const std::string&`.

### Prompt 2

```cpp
void append_exclamation(const std::string& s) {
    s += "!";
}
```

Response: the function tries to modify a const argument, which is not allowed.

Takeaway: mutating the caller's string requires `std::string&`.

### Prompt 3

```cpp
const std::string& make_name() {
    std::string name = "Grace";
    return name;
}
```

Response: `name` falls out of scope after the function returns; the returned reference lives on.

Correction: the reference does not keep the object alive; it dangles after `name` is destroyed.

Takeaway: return by value for locally created objects.

### Prompt 4

```cpp
void store_pointer(const int* p) {
    static const int* saved = nullptr;
    saved = p;
}

int main() {
    int x = 42;
    store_pointer(&x);
}
```

Response: initially thought `saved` falls out of scope at the end of `store_pointer`.

Correction: because `saved` is `static`, the pointer variable persists. The risk is that it may point to an object whose lifetime has ended.

Takeaway: a stored pointer can become dangling even if the pointer variable itself is still alive.

## Mistakes To Review

- Distinguish the lifetime of a pointer/reference variable from the lifetime of the object it refers to.
- Be precise about `const std::string` object versus `const std::string&` reference.
- Remember that `std::move` enables ownership transfer; the moved-from `std::unique_ptr` is empty afterward.
